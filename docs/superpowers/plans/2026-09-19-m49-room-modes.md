# M49: Room modes and on-call answers

Status: implementation complete and independently reviewed, 2026-09-21; final automated and release gates pending. Full scope authorized by the owner. Main session owns delivery through release; the independent Sol reviewer passed the sensitive design, corrected source, and candidate browser evidence. This concise delivery plan supersedes the earlier blocked planning draft and its retired scored-review ceremony.

Risk: sensitive (schema 15, paid dispatch admission, child-process isolation and cancellation). Objective: ordinary owner messages receive bounded on-call answers with honest mode, participants and turn cost before sending. Non-goals: persistent model sessions, run-engine redesign, hostile-process isolation, remote access and paid usage estimates.

## Acceptance

- A1: When a fresh or v14 room is opened, it reports relay mode and the ordered on-call pair Astra then Opus. The owner can set `/mode relay`, `/mode primary`, or `/mode panel`, optionally followed by one or two ordered leading participant ids as appropriate. Invalid names, duplicates, non-spawnable participants, malformed arguments, and insufficient participants spend zero turns and preserve the previous settings. Settings survive restart. The header exposes the same controls and their saved state.
- A2: When an owner posts an ordinary unaddressed message outside a run, primary launches exactly the first configured participant once. Relay launches that participant, waits for its completed answer, then launches the second with the first answer explicitly included, even beyond the transcript window. No model mention can add an unplanned turn. A failure or empty first answer ends relay with an actionable note and no second charge. Each successful relay has exactly two model launches.
- A3: When the owner chooses panel, both first passes receive the same frozen transcript, governing revision, room persona, memory, and optional repository snapshot. They may differ only in self identity and configured role. Both may run simultaneously, subject to existing per-participant spacing and in-flight limits. Neither first-pass answer is made available through the hub before both first passes finish. Then the first participant synthesizes both labelled outcomes in one reserved turn. The UI calls this an answer/review mode, with no file edits. It must not claim hostile-process or OS-level isolation.
- A4: When a mode turn is stopped, superseded, continued, replied to, fails, or overlaps other room activity, the exact root retains correct lifecycle and turn counters. Stop prevents all not-yet-launched work including synthesis. Duplicate message notifications never buy another turn. Imported history, model-authored messages, governing commands, invalid slash commands, and active-run steering never trigger on-call fallback. Explicit leading mentions retain the existing explicit-address exchange path, including its budget and continuation rules.
- A5: Before send and during execution, the header, recipient preview, and exchange strip show mode, ordered participants, and planned/started/remaining turns. Primary advertises 1, relay 2, panel 3, including synthesis. Any supplied `turns:` value below the required mode cost refuses before launch. Cost in money and tokens is shown as unknown, never zero or an invented price. State remains correct across room switches, reconnect, and simultaneous exchanges. Real UIA clicks and viewed captures prove the controls.
- A6: A raw v14 fixture migrates without changing messages, imported provenance, reply ids, governing revisions, participant roles, or existing room directories. Interrupted or failed migration preserves a verified backup and is retryable. Old JSON without new properties decodes to documented defaults. No resume/session ids or credential persistence are introduced. Existing run, mention, continue, worktree, attribution, and governing-context regression suites remain green.

## Implementation contract

- New and migrated rooms default to relay, Astra then Opus. Stored settings have a revision. Invalid commands preserve settings. Old payloads without settings show unavailable until authoritative settings are fetched.
- The existing single-reader spawner loop owns quote validation, message persistence and dispatch. Quotes expire after two minutes, bind exact author/body/room/reply, room settings/directory/archive, run and exchange state, and panel Git HEAD. Bound quote storage to 256. A stale quote refuses before storage or reservation. Identical client-key retries return the accepted message without spending again; altered retries refuse. Unquoted authenticated API/MCP callers remain supported without an earlier-preview guarantee.
- Explicit leading recipients, imported history, governing commands, skills and run routing retain their established paths. A completed mode can continue with its frozen mode/pair or transition to explicit continuation. A live or finishing mode records unaddressed reply steering without extra turns. Supersession and stop discard pending work; duplicate notifications do not dispatch twice.
- Primary costs one turn. Relay costs two and uses successful completed posted answers, or final output when no posts exist. Posted answers are ordered, joined once, bounded to 20,000 characters with disclosure; an empty, failed, cancelled or timed-out first process never starts the second.
- Panel reserves three turns. Freeze transcript/governing/persona/memory and roles once. Prepare snapshots off the event loop with cancellation and root/leg identity checks. Hold first-pass answers until both finish, publish in configured order, synthesize available outcomes once; missing outcomes are labelled unavailable. Stop/supersession prevent synthesis.
- A directory panel requires clean committed Git HEAD. Read exact blobs through ls-tree/cat-file (archive attributes cannot omit or rewrite content). Materialize separate first/second/synthesis directories with no .git; cap 10,000 entries and 100 MiB, reject links/submodules, traversal, unsafe Windows names and collisions. Revalidate admitted HEAD before and after preparation. Plain-room panels use empty directories. Remove only newly allocated private panel roots.
- Panel CLIs receive no hub MCP configuration or inherited CHOPITUP/API-key variables. Claude uses Read/Glob/Grep and strict empty MCP configuration; Codex uses explicit read-only unelevated Windows sandbox and approval never. Ignore user configuration. Capture at most 1 MiB per output pipe and kill the process tree on overflow. The permission boundary is tested, not described as protection against a malicious local process.
- Schema migration is transactional, backup precedes migration, existing content/provenance/roles/directories remain intact, and missing version stamps retain the existing idempotent repair path. No session credentials or model resume IDs are persisted.
- Header settings, server-resolved composer previews and exchange strips show costs/order; refresh settings on room mode events and reconnect. A mode Continue validates the displayed mode/pair against a fresh quote and leaves unrelated drafts untouched. A stale send preserves the draft and requires another click.

Design corrections required by independent source review:

1. Quotes include room Directory and IsArchived values in addition to settings revision, run and target lifecycle. Owner admission re-reads all fields in the event loop before storing or reserving, and rejects mismatches. Directory and archive mutation must enter the same loop, so no HTTP mutation races the admission decision. Tests bind/archive between preview and Send, including concurrent serialization. HTTP sends acquire a stable client key retained for transport retries. Same-key changed-body, changed-reply or changed-room retries refuse. Same-key identical successful requests return the original message/dispatch despite consumed/expired quotes. Failed persistence does not consume a quote or reserve a turn. Signal duplicates cannot relaunch admitted work.
2. Panel preparation runs outside the single-reader loop with its own cancellation source. A prepared event carries root id and leg generation. The loop accepts only the still-current, not-stopped leg. A stopped/superseded completion disposes its own snapshot and cannot launch. Keep the snapshot until every associated process is finished. Tests hold preparation, send in another room, stop the root, then release preparation and assert no launch. Snapshot preflight/refusal is visible before spending, with no silent retry after repository changes.
3. Successful primary/relay answers require exit code zero and no timeout/cancellation/output-limit condition. Use participant-attributed MCP posts for that spawn in publication order as the canonical answer when present, otherwise a nonempty supported final CLI result is published as a root-linked participant answer. Multiple posts are joined with visible separators and the 20,000-character bound/disclosure. Never concatenate both posted answers and duplicate final output. Nonzero exit remains failure even if a post exists. Final-only, posted-only, multiple-post, post+nonzero and empty cases are required tests. Only process completion can schedule the second relay turn.

Private raw probe/review/usage evidence stays in the existing measured delivery record outside this public repository. The earlier blocked draft has been superseded; final independent review and release evidence remain in the private delivery record.
4. Directory-panel preview readiness includes the exact immutable Git commit id. Quote binds that id. At admission a bounded read-only Git preflight verifies the repository is still clean/conflict-free and HEAD is that quoted id before message storage or reservation. A changed commit or readiness returns 409 and requires a fresh Send. Preparation materializes exactly the admitted id and still validates cleanup/cancellation and the post-materialization HEAD/clean check before launch. Test preview at clean A, advance clean HEAD to B, then Send: 409 with zero stored owner message and zero model launches.

Final review corrections: release collected panel outcomes when superseded with no running process; off-handle model content never expands a mode root; owner retry keys bind their original room; recheck exact Git root and clear inherited Git routing variables; move Git preflight and snapshot cleanup off the event loop; retain bounded recent/pending signal suppression. Targeted tests cover these failure mechanisms. No durable dispatch ledger is introduced.
